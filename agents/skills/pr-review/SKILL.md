# PR をレビューする（pr-review）

**コードを書き換えない。** 動作確認 skill が確認のために一時的に変えて戻すものだけは例外とする。GitHub には、`-p` のときに pending レビューとしてコメントを置くだけで、submit しない。

## 引数

```text
/pr-review [PR] [-n | -v] [-p] [-s]
```

すべて省略でき、順不同。1 文字のオプションはまとめて書ける（`-ps`）。

- **PR**: URL か番号。省略時はカレントブランチの PR。
- **`-n`（`--no-verify`）**: 動作確認をしない。
- **`-v`（`--verify-only`）**: 動作確認だけをする。手順 4・5 を飛ばす。
- **`-p`（`--post`）**: 手順 7 で指摘を pending レビューに置く。
- **`-s`（`--stay`）**: 作業スペースを worktree へ移さない。

どれも無ければ、コードレビューの後に動作確認をする。動作確認を飛ばす条件は手順 6 に書く。

`-n` と `-v` が両方ある場合と、どれにも当たらない引数がある場合は、何も実行せずに引数の形を示して終了する。

他の skill を呼べない環境では、この SKILL.md の実体（シンボリックリンクを解決した先）と同じ skills ディレクトリにある `<skill 名>/SKILL.md` を読んで従う。別のエージェントを起動できない環境では、そう伝えて手順 4・6 を自分で行う。

## 手順

### 1. PR を確かめる

```bash
gh pr view <PR> --json number,url,state,baseRefName,headRefName,headRefOid,isCrossRepository
gh pr diff <PR> --name-only
```

PR が無い、または `state` が `MERGED` か `CLOSED` なら、理由を示して終了する。

次の場合は、PR の作者が書いた設定・hook・指示が、worktree へ移った後のエージェントや worktree で実行するコマンドで動く。該当するファイルを示し、続けてよいかユーザーに確認する。承認が得られなければ終了する。

- `isCrossRepository` が true（フォークの PR）。
- 変更ファイルに `.claude/`、`.codex/`、`.agents/`、`CLAUDE.md`、`CLAUDE.local.md`、`AGENTS.md`、`.mcp.json`、`.husky/`、`.githooks/` のいずれかが含まれる。
- 変更ファイルに、`git config core.hooksPath` が相対パスで指すディレクトリのファイルが含まれる。

この確認を、review-code の手順 4 と動作確認 skill が求める「PR のコードを実行する前の確認」に代える。

### 2. worktree を用意する

`git mkwt <番号>` を実行する。標準出力に worktree の絶対パスが出る。

- 「既にチェックアウトされています」で失敗したら、標準エラーに出たパスの worktree を使う。カレントの作業ツリーのこともある。
- それ以外で失敗したら、標準エラーを示して終了する。`git mkwt` が PATH に無いときも、そう伝えて終了する。

worktree がカレントの作業ツリーなら、この手順の `git -C <worktree>` は `-C <worktree>` を外して実行する。worktree に隔離されたセッションは、`-C` で場所を指定した git を拒否する。worktree がカレントでなく、`git -C <worktree>` が拒否されたら、中断として終える。隔離されたセッションからは、別の worktree へ移ることも、そこを操作することもできない。「次にすること」には、worktree の絶対パスと、そこで新しいセッションを開くことを書く。

worktree を PR の head に合わせる。

1. `git -C <worktree> status --porcelain` が空でなければ、未コミットの変更があることを伝えて終了する。
2. `git -C <worktree> rev-parse HEAD` が手順 1 の `headRefOid` と違えば、次で合わせる。

```bash
git -C <worktree> fetch origin "pull/<番号>/head"
git -C <worktree> merge --ff-only FETCH_HEAD
```

3. 合わせた後も HEAD が `headRefOid` と違えば、状況を伝えて終了する。push していないコミットがあると、merge は成功しても HEAD は先に進んだままになる。

差分の範囲を決める。差分が空なら終了する。

```bash
git -C <worktree> fetch origin "<baseRefName>"
git -C <worktree> merge-base "origin/<baseRefName>" HEAD
```

出力された commit を `${MB}` とし、`git -C <worktree> diff --name-status <MB> HEAD` を実行する。git の出力をコマンド置換で受ける形も、隔離されたセッションでは拒否される。

### 3. 作業スペースを worktree へ移す

`-s` が無く、worktree がカレントの作業ツリーでなければ、使える道具で作業スペースを worktree へ移す（Claude Code では `EnterWorktree` に `path` を渡す）。移したら `pwd` が worktree を指すことを確かめる。

移せなかったとき（道具が無い、承認されない、道具が拒否した）は、そう伝えて移さずに進める。その場合、以降の作業は次のように worktree へ向ける。カレントのまま実行すると、別のブランチを PR として読んでしまう。

- `git` は `git -C <worktree>` で実行する。
- ファイルは worktree の絶対パスで読む。
- カレントディレクトリに依存するコマンドは `(cd <worktree> && <コマンド>)` で実行する。

### 4. コードをレビューする

会話の文脈を引き継がない別のエージェント（Claude Code では `subagent_type: "general-purpose"` の Agent。fork は使わない）を 1 つ起動し、結果が返るまで待つ。prompt に書くもの。

- worktree の絶対パス、PR の番号、`${MB}`。作業スペースを移していなければ、手順 3 の箇条に従うこと。
- この SKILL.md の絶対パスを読み、「コードレビューの中身」の節を実行し、その節の「返すもの」だけを返すこと。review-code の「実行する者」の節は飛ばし、自分で行うこと。
- PR のコードを実行する確認は済んでいること。
- ファイルを変更しないこと。GitHub に投稿しないこと。

### 5. must の候補を反証する

指摘を出したサブエージェントとは別の者として、自分で確かめる。手順 4 を自分で行った場合は、同じ者が確かめたことを出力の「補足」に書く。

- 場所を持つ候補は、該当コードと周辺を読み、起きない理由を探す側から確かめる。確かめ方に実行した手順があれば、再実行して同じ結果になるかを見る。
- 受入条件の候補は、資料と差分を突き合わせ、満たす変更が本当に無いかを確かめる。

確かめた結果、起きる（満たす変更が無い）なら must、起きない理由を示せたら判定対象外、どちらとも言えなければ should にする。

### 6. 動作確認する

`-n` のときは行わない。それ以外で、次のどちらかに当たれば飛ばし、飛ばした理由を出力に書く。`-v` のときも同じ。

- 差分のファイルがすべて、ドキュメント・テスト・CI の設定・型定義のどれか。画面や挙動が変わらない
- worktree に `.claude/skills/verify/SKILL.md` も `.agents/skills/verify/SKILL.md` も無い。汎用の手順で代わりにしない。プロジェクトの skill が持つ、DB の接続先の確認などの安全策を通らなくなるため

手順 4・5 で must が出ても、動作確認まで続ける。must を画面やデータで再現できれば、指摘の裏付けになる。

verify は手動起動専用なので、skill としては呼ばない。手順 4 と同じ種類のエージェントに SKILL.md を読ませて実行させる。prompt に書くもの。

- worktree の絶対パスと PR の番号。作業スペースを移していなければ、手順 3 の箇条に従うこと。
- 動作確認 skill の SKILL.md の絶対パスを読み、その手順で確認すること。PR のコードを実行する確認は済んでいること。
- 確認の観点に足すもの: 手順 4・5 の must と should のうち、画面やデータで確かめられるもの。
- ユーザーの承認・操作・入力が要る手順（DB の作り直しの承認、ログインの代行など）と、アプリや Storybook などのサーバの起動の手前で止まり、何が要るかとそこまでの結果を返すこと。サーバの起動では、起動するものと、動作確認 skill の起動の手順の場所を返すこと。
- 最後に返すもの: 確認できたこと（UI の操作・API の直接検証・自動テストに分ける）、確認できなかった観点と理由、証跡の保存先、見つけた不具合と再現手順。

止まって返ってきたら、要るものをユーザーに確かめ、結果を同じエージェントに伝えて続けさせる（Claude Code では SendMessage）。続けさせられなければ、残りを自分で行う。

アプリや Storybook などのサーバの起動を求めて止まった場合は、動作確認 skill の起動の手順を、サブエージェントではなく自分で行う。コマンドは worktree でバックグラウンドで実行する（Claude Code では Bash の `run_in_background`）。サブエージェントが終わっても止まらないようにするため。起動できたら、URL を添えて同じエージェントに続けさせる。

終わったら `git -C <worktree> status --porcelain` を見る。空でなければ、残っている変更を出力に載せる。消さない。

見つけた不具合は、review-code の手順 6 の定義で区分して指摘に足す。再現手順で確かめたものなので、反証はしない。

### 7. pending レビューに置く

`-p` のときだけ行う。pr-pending-review skill の手順で置く。渡すものは、PR、手順 1 の `headRefOid`、手順 4〜6 の指摘のうち判定対象外を除いたもの。置けなかったコメントは手順 8 の「置けなかったコメント」に載せる。

### 8. 出力する

チャットはログのように流れて読まれるので、詳細を先に、要点を最後に置く。読み手が最後の「結論」だけを読めば、結果と次にすることが分かるようにする。

判定は、ある区分のうち最も重いもので決める。must は「要修正」、should は「修正推奨あり」、question は「確認事項あり」、それ以外は「指摘なし」。nit と follow-up は判定に使わない。

```markdown
### 詳細

#### 1. [must] <問題を 1 行で>
- 場所: `<ファイル:行>`
- 何が起きるか: <入力・状態・結果>
- 影響: <誰に何が起きるか。起きる条件が通常の操作でどれだけ起きるか。この PR で入った退行か、既存の挙動か>
- 確かめ方: <追った行、実行したコマンドと結果の要約 1 行、動作確認の操作。実行していなければそう書く>
- 直し方: <1〜2 文>

（should・question も同じ形。nit・follow-up は「#### N. [nit] `<場所>` <問題>」の 1 行だけ）

### 置けなかったコメント

- 指摘 <N>（`<パス>:<行>`）: <本文>

### 動作確認

- 確認できたこと: <操作と結果。UI の操作・API の直接検証・自動テストを分ける>
- 確認できなかったこと: <観点と理由>
- 証跡: <保存先>

### 補足

- 受入条件: 充足 <N> 件、未充足 <N> 件（指摘 <N>）。取得できなければその理由
- 読めなかった資料: <URL と理由>
- 反証で外した must 候補: <件数と代表的な理由>
- 当てた REVIEW.md の項目: <項目と、指摘につながったか>

## 結論: <要修正 / 修正推奨あり / 確認事項あり / 指摘なし>（<0 件でない区分ごとの件数>）

対象: <PR URL>（head <SHA 先頭 7 桁>）
実施: コードレビュー、動作確認（<全部 / 一部 / 未実施。一部・未実施は理由>）

1. [must] `<場所>` <問題を 1 行で>
2. [should] `<場所>` <問題を 1 行で>
3. [nit] `<場所>` <問題を 1 行で>

次にすること:
- pending レビューを確かめて submit する（<N> 件を置いた。<PR のリンク>）
- 残っている一時的な変更を確かめる: `<パス>`
- 手順 6 で起動したサーバを、不要なら止める: <止め方>（<URL>）
- 元のディレクトリへ戻る: <戻り方>（worktree: <絶対パス>）
```

- 番号は重さの順に通しで振り、詳細と結論で同じ番号を使う。結論には全区分の指摘を 1 行ずつ載せる。
- 表は使わない。狭いペインでは列が切れて、問題の文が読めなくなる。
- 書くことの無い節と行は出さない。指摘が無ければ「詳細」を出さない。作業スペースを移していなければ、戻る行は出さない。
- 戻り方は、Claude Code では `ExitWorktree` の `keep`。
- サーバの止め方は、Claude Code では起動したバックグラウンドのタスクの `TaskStop`。

途中で終了したときは、詳細を出さずに次だけを出す。

```markdown
## 結論: 中断（手順 <N> で停止）

理由: <1 文>
残したもの: <作った worktree の絶対パス、移した作業スペース。無ければ「なし」>
次にすること: <例: 手元のコミットを push してから再実行する>
```

## コードレビューの中身

手順 4 で行う。worktree・PR の番号・`${MB}` は渡されたものを使う。

### 資料を読む

```bash
gh pr view <番号> --json body,comments,reviews,closingIssuesReferences
gh api "repos/{owner}/{repo}/pulls/<番号>/comments" --paginate
```

PR 本文とコメントにあるリンク、`closingIssuesReferences` の issue を 1 次資料として、read-sources skill の手順で読む。読んだ資料から次を控える。

- review-code の手順 2 の「仕様」「規約」「決着済み」。
- 既存のレビューのスレッドで指摘済みの事項。resolve 済みで方針が決まったものは決着済みに入れる。未解決のスレッドと同じ内容の指摘は、そのスレッドの URL を添えて返し、スレッドに無い新しい根拠があるときだけ pending レビューに置く対象にする。
- 受入条件の箇条書きと、それぞれの出どころ（資料と箇所）。
- 資料どうし、または資料と PR 本文の食い違い。どれが新しい決定かを、日付・改訂の記述・他の資料との一致で確かめる。

### review-code の手順でレビューする

review-code skill の手順で、`${MB}...HEAD` をレビューする。review-code の手順 1 の確認は pr-review の手順 2 で、手順 2 の read-sources で読む資料は上で済んでいるので繰り返さない。手順 2 の `REVIEW.md` と、変更が依存するコードは読む。

### 受入条件と差分を突き合わせる

受入条件を 1 つも取得できなければ飛ばし、理由を返す。

- 受入条件ごとに、満たす差分の場所を対応させる。PR が対応すると書いているのに満たす変更が無い条件は、must の候補にする。
- 資料の一部だけが古いと示せた条件は、「資料の更新漏れ」として should にする。示せなければ資料の記述を正とする。
- 資料に無く PR 本文にも説明が無い変更と、意図して範囲外にしたのに PR 本文にその旨が無い受入条件は、should にする。

### 返すもの

- 指摘: review-code の手順 6 の形。must は候補として返す。
- 受入条件: 充足した件数と、未充足の条件。
- 読めなかった資料と理由、当てた `REVIEW.md` の項目、出さなかった候補の件数の内訳。review-code の手順 6 の最後の行と同じ形で返す。
