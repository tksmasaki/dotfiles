# PR の網羅レビュー（pr-fullcheck）

**このスキルはコードを書き換えず、GitHub にも投稿しない（report only）。** レビュアーモードでも、
コメントは下書きを示すだけにする。投稿はユーザーが頼んだときに、このスキルの外で行う。

## 引数

```text
/pr-fullcheck [PR URL か番号] [-r] [-s]
```

すべて省略でき、順不同。形で判別する。

- **PR**: `https://github.com/<owner>/<repo>/pull/<番号>` か番号。省略時はカレントブランチの PR。
- **`-r`**: レビュアーモード。無ければ実装者モード。
- **`-s`**: 手順 1〜6 をサブエージェントに実行させる。メインの文脈にレビューの途中経過を残さないため。進め方は「サブエージェントで実行する（-s）」に従う。別のエージェントを起動できない環境では、そう伝えて `-s` なしで進める。

どれにも当たらない引数があれば、何も実行せずに引数の形を示して終了する。

モードで変わるのは手順 1 の作成者の確認と、手順 6 の判定とレポートの形だけ。読む資料とレビューの手順は同じ。

## 手順

### 1. 対象を確定する

```bash
gh pr view <PR> --json number,url,title,author,baseRefName,headRefName,headRefOid,isDraft
gh api user --jq .login
```

次の場合は、何も実行せずに理由と次の操作を示して終了する。

- PR が無い。
- 実装者モードで作成者が自分でない。`-r` を付けて実行し直すよう案内する。
- レビュアーモードで作成者が自分。`-r` を外すよう案内する。
- ローカルの `HEAD` が `headRefOid` と一致しない。`gh pr checkout <番号>` などで head に合わせるよう案内する。
- `git status --porcelain` が空でない。未コミットの変更を片付けるよう案内する。

続けて、作業ツリーの絶対パス、base との merge-base、差分ファイル一覧を確定し、以降の手順でこれを使う。

```bash
TOP=$(git rev-parse --show-toplevel)
BASE=<baseRefName>
git fetch origin "${BASE}"
MB=$(git merge-base "origin/${BASE}" HEAD)
git diff --name-status "${MB}" HEAD
```

差分が空なら終了する。

### 2. PR と関連資料を読む

PR 本文だけで判断しない。条件の詳細や改訂後の方針は、コメントやリンク先にあることが多い。

```bash
gh pr view <番号> --json body,comments,reviews,closingIssuesReferences
gh api "repos/{owner}/{repo}/pulls/<番号>/comments" --paginate
```

PR 本文と PR のコメントにあるリンク、`closingIssuesReferences` の issue を 1 次資料として、read-sources skill の手順で読む。コメントを絞るときは、PR の変更に関わる箇所に付いたものに絞る。呼べない環境では、この SKILL.md の実体と同じ skills ディレクトリにある `read-sources/SKILL.md` を読んで従う。

返った一覧は、レポートの「読んだ資料」と「読めなかった資料」に載せる。

読んだ資料から次を控える。

- review-code の手順 2 の「仕様」「規約」「決着済み」。
- 受入条件の箇条書きと、それぞれの出どころ（資料と箇所）。
- 既存のレビューのスレッドで指摘済みの事項と、resolve 済みかどうか。
- 資料どうし、または資料と PR 本文の食い違い。どれが新しい決定かを、日付・改訂の記述・他の資料との一致で確かめる。

### 3. review-code の手順でレビューする

review-code skill の手順で、`${MB}...HEAD` をレビューする。呼べない環境では、この SKILL.md の実体と同じ skills ディレクトリにある `review-code/SKILL.md` を読んで従う。

- review-code の手順 1 の確認は、この skill の手順 1 で済んでいる。
- review-code の手順 2 の資料は読み直さず、この skill の手順 2 で控えたものを使う。
- レビュアーモードでは PR の作者のコードを実行することになる。rv-pr から呼ばれた場合は、rv-pr の手順 1 で確認済みとして扱う。直接呼ばれた場合は、review-code の手順 4 に従ってユーザーに確認する。

### 4. 受入条件と差分を突き合わせる

手順 2 で受入条件を 1 つも取得できなければスキップし、理由をレポートに書く。

- 受入条件ごとに、満たす差分の場所を対応させる。満たす変更が無い条件を挙げる。
- 資料の一部だけが古いと示せた条件は、「満たす変更が無い」ではなく「資料の更新漏れ」として挙げる。示せなければ資料の記述を正とする。
- 資料に無いのに差分に入っている変更を挙げ、PR 本文に説明があるかを見る。

結果は review-code の区分に足す。

- PR が対応すると書いているのに満たす変更が無い受入条件は、must の候補にする。
- 資料の更新漏れ、資料に無く PR 本文にも説明が無い変更、意図して範囲外にしたのに PR 本文にその旨が無い受入条件は、should にする。

### 5. must の候補を反証する

must の候補を、報告の前に 1 つの別のエージェント（Claude Code では general-purpose）にまとめて渡し、反証させる。指摘を出した側とは別の者に確かめさせるため。別のエージェントを起動できない環境では、自分で同じ手順を行い、そう明記する。

渡すもの。

- 作業ツリーの絶対パス `${TOP}` と、差分の範囲。
- 候補ごとの場所・何が起きるか・確かめ方・根拠。
- 場所を持つ候補は、該当コードと周辺を読み、問題が実際に起きるかを、起きない理由を探す側から確かめること。review-code の確かめ方に実行した手順があれば、再実行して同じ結果になるかを見ること。
- 受入条件の候補は、手順 2 の資料と差分を突き合わせ、満たす変更が本当に無いかを確かめること。
- 候補ごとに `成立`（起きる・満たす変更が無い）/ `不成立`（理由を添える）/ `判断不能` を返すこと。ファイルを変更しないこと。

`成立` は must に、`不成立` は判定対象外に、`判断不能` は should にする。`不成立` と `判断不能` は理由をレポートに残す。

### 6. 判定してレポートする

区分は review-code の手順 6 の定義に従う。

- **実装者モード**: must があれば「要修正」、should か question があれば「修正推奨あり」、どれも無ければ「レビュー依頼OK」。
- **レビュアーモード**: must があれば Request changes、should か question があれば Comment、どれも無ければ Approve を推奨する。決めるのはユーザーなので、推奨と書く。

区分ごとに一覧を出す。nit・follow-up・判定対象外も省略せず全件載せる。判定に使わない指摘を隠すと、読み手が取捨選択できなくなる。

```markdown
## PR 網羅レビュー結果（実装者 / レビュアー）

対象 PR: <PR URL>（base: <baseRefName>、head: <head SHA 先頭7桁>、作成者: <login>）

### 判定: <実装者: レビュー依頼OK / 修正推奨あり / 要修正。レビュアー: Approve / Comment / Request changes を推奨>

<区分ごとの件数>

### must

**#1 <問題を 1 行で>**
- 場所: `<場所>`
- 何が起きるか: <入力・状態・結果>
- 確かめ方: <実行したコマンドと出力、追った行、規約の箇所。反証の結果も>
- 根拠: <仕様・規約・資料の箇所>
- 既存スレッド: <指摘済みならスレッドと状態。無ければこの行を省く>
- コメント案: <レビュアーモードだけ。下の「コメント案の書き方」に従う>

### should

（同じ形式）

### question

（同じ形式）

### nit

- #N `<場所>`: <問題>

### follow-up

- #N `<場所>`: <問題>

### 判定対象外

- #N `<場所>`: <問題>。対象外とした理由: <反証で不成立、など>

### 受入条件の充足（出どころ: <資料>）

- 充足: <条件>（<満たす変更の場所>）
- 未充足: <条件>（#N）

### 出さなかった候補

- <review-code の手順 6 の件数の内訳>

### 読んだ資料

- 1 次: <URL>（<種類>）
- 2 次: <URL>（<種類>）
- 3 次（未取得）: <URL>

### 読めなかった資料

- <URL>: <理由>

### 次のアクション
```

- 表は使わない。狭いペインでは列が切れて、問題の文が読めなくなる。
- `#` は区分を通して振る。「次のアクション」から番号で引けるようにするため。
- 区分が空なら「なし」と 1 行で書く。受入条件の観点をスキップしたら、その節は出さず理由を「出さなかった候補」の後に書く。
- 「次のアクション」は、実装者モードでは作者が直すことを、レビュアーモードではコメントを付ける順と、確かめが要る点を書く。

#### コメント案の書き方（レビュアーモード）

ユーザーが削って使う前提なので、簡潔さより材料の多さを優先する。

- 何が起きるかを、入力・状態・結果の具体例で書く。
- 根拠のコードの場所と、資料の該当箇所を書く。
- 直し方の案を 1 つ添える。断定できない点は質問の形にする。
- 作成者に宛てた敬体で書く。

## サブエージェントで実行する（-s）

### 1. サブエージェントに手順 1〜6 を実行させる

会話の文脈を引き継がない別のエージェント（Claude Code では `subagent_type: "general-purpose"` の Agent。fork は使わない）を 1 つ起動し、レポートが返るまで待つ。

prompt に書くもの。

- 作業ディレクトリの絶対パス（`git rev-parse --show-toplevel` の出力）。
- この SKILL.md の絶対パスを読み、手順 1〜6 を実行すること。
- 引数は `-s` を除いた残り。解釈は「引数」に従うこと。
- 最終出力は手順 6 のレポートだけにすること。途中のログは含めない。
- 手順 1 などの中止条件で終了した場合は、中止した理由と案内だけを返すこと。
- コードを書き換えないこと。GitHub に投稿しないこと。

中止の報告が返った場合は、それをそのまま示して終了する。

### 2. 区分を判定しなおす

レポートの全指摘について、場所のコードを読み、review-code の手順 6 の定義で区分を付け直す。場所を持たない指摘は、差分とレポートの「受入条件の充足」から判断する。

- 区分を変えるのは、コードを読んで事実の見立てが変わったときだけにする。基準はサブエージェントと同じなので、見立てが同じなら区分も同じになる。
- 判断がつかなければ元の区分を残す。ただし must は、確証を取れなければ should に下げる。

### 3. 組み直して示す

付け直した区分で、判定と区分ごとの一覧を手順 6 の形式で組み直す。`#` は組み直した順に振り直す。

- 指摘は 1 件も落とさない。区分ごとの件数の合計を、サブエージェントのレポートの件数と一致させる。
- 区分を変えた指摘には、元の区分と変えた理由を添える。1 件ずつ書く区分では「区分の変更」の項目を足し、1 件 1 行の区分では行末に書く。
- 「受入条件の充足」「出さなかった候補」「読んだ資料」「読めなかった資料」は、サブエージェントのレポートをそのまま載せる。受入条件の充足が引く `#N` だけは振り直した番号に合わせる。
- 「次のアクション」は、付け直した区分から書き直す。
