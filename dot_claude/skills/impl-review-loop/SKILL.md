# 実装レビューループ

**レビュー側のセッションで起動する。** このスキルはコードを書き換えない。レビュー側が直接触ると実装側の作業ツリーと衝突し、どちらの変更か追えなくなる。実装側が守る作法は最後の節にまとめてあるので、実装側はそこだけ読めばよい。

## 引数

**引数の解釈は位置ではなく形で決める。**

- `https://` で始まる、`#` 付き数字、裸の数字: PR の指定
- `low` | `medium` | `high` | `xhigh` | `max`: effort（既定は `high`）
- `--rounds N`: 上限周回数（既定は 5。1 以上の整数）
- それ以外: 対象の説明として扱う

**上限周回数は `--rounds` でしか渡らない。** 裸の数字は常に PR 番号として扱う。`--rounds` に 1 未満や整数でない値が来たら意味を尋ねる。読み替えない。

## 0. 初期化（起動時に 1 度だけ）

レビュー範囲・effort・上限周回数・締めの工程をここで決めて台帳の冒頭に書き、周ごとに引き直さない。**相手の宛先だけは毎周引き直す。**

### 相手を同じ worktree で特定する

**実装側とレビュー側が同じ worktree で動くことが前提。** レビュー範囲が未コミットの作業ツリーになる以上、別 worktree の相手とは組めない。

`ListAgents` の一覧は名前と `ref` だけで作業ディレクトリを含まず、名前は worktree をまたいで重複する。別々の worktree の `impl` が 2 つ並ぶ状態は普通に起きる。**一覧を眺めて worktree を当てない。** 同じ作業ツリーのセッションは send-msg の補助スクリプトで引く。

```bash
~/.claude/skills/send-msg/peers.sh
```

出力は `self|same|other`・名前・`ref`・状態・作業ディレクトリのタブ区切りで、`same` が同じ作業ツリー。**`名前 [ref]` の組が `ListAgents` の行と一致したときだけ宛先にできる。**

**起動したら、名前が役割と一致していても自分の役割を書く。** `2-fasrtse` のような自動命名では、どれがレビュー側かは名前からは決まらない。書かないと、あとから加わったセッションが宛先を解決できずソケットパスの直接指定に逃げることになる。

```bash
~/.claude/skills/send-msg/role.sh set review
~/.claude/skills/send-msg/role.sh list
```

役割ファイルは `$(git rev-parse --absolute-git-dir)/claude-roles/<役割>` に置かれる。`--absolute-git-dir` は linked worktree なら `.git/worktrees/<名前>`、main worktree なら `.git` を返す。**どちらも作業ツリーの外なので、`git status` にも PR の差分にも出ない。**

宛先は次の順で決める。**どの段でも推測で送らず、ソケットパスの直接指定にも逃げない。**

1. `role.sh get impl` が `名前 [ref]` を返すなら、それを宛先にする
2. 返さなければ `same` の行で名前が役割そのもの（`impl`）のものを取る。**1 件ならそれを宛先にする。** 同じ作業ツリーでその名前を名乗っている以上、確認は要らない
3. 1 件に絞れないなら、`same` から自分を除いた行を `AskUserQuestion` で並べて選んでもらう
4. `same` が自分だけなら、同じ worktree に相手はいない。`--all` で同名がどこにいるかを示し、ユーザーの指示を仰ぐ

**相手の役割ファイルが無いときは、相手がこのスキルを読んでいない。** 差し戻しの作法を共有していないので、最初の 1 通に返信の形（修正した点・方針を変えた点・反論する点を分け、反論には `ファイル:行` か実行結果を付ける）を書き添える。2 通目以降は繰り返さない。

**`ref` は毎周引き直す。台帳に控えた `ref` を次の周で使い回さない。** 差し戻す直前に `role.sh get` と `ListAgents` を引き直し、相手が生きていることをその場で確かめる。

### レビュー範囲を確定する

```bash
git status --porcelain
git rev-parse HEAD
if git rev-parse --verify --quiet @{upstream} >/dev/null; then
  git log --oneline @{upstream}..HEAD
else
  echo "upstream 未設定: ブランチ固有コミットはこの方法では判定できない"
fi
```

PR の指定があれば head も取る。

```bash
gh pr view <PR番号> --json number,headRefName,headRefOid
```

`headRefOid` がローカルの `HEAD` と一致し、作業ツリーがクリーンなら **PR を対象にする**。そうでなければ **未コミットの作業ツリーを対象にする**。決めた範囲と根拠を台帳に書き、作業ツリーを対象にした場合は、実装側の commit や amend のたびに範囲が動くことも書いておく。範囲を各周のレビュアーに委ねると、同じ確認を毎周繰り返したうえで結論がずれる。

**`|| git log --oneline -5` のようなフォールバックを書かない。** upstream 未設定のリポジトリでは無関係な直近コミットが終了コード 0 で返り、ブランチ固有コミットと区別できなくなる。判定できないことは、判定できないと出す。

### 判定台帳を作る

**リポジトリの中に作らない。** セッションの scratchpad ディレクトリに `review-ledger.md` として置く。作業ツリーに置くと PR に余計な差分として混ざる。

```markdown
# レビュー判定台帳: <対象>
- worktree: <トップレベルのパス>
- 相手: <名前 [ref]>（role.sh get impl から取得。最後に確認した周: <n>）
- レビュー範囲: <PR #NNNN / 未コミット作業ツリー>（根拠: ...）
- effort: <レベル> / 上限: <N> 周
- 締めの工程: <指定があれば。無ければ「なし」>

## 周回
| 周 | 新規 | 既出 | 差し戻し |
|----|------|------|----------|

## 判定済みの指摘
| # | 箇所 | 要約 | 判定 | 判定者 | 初出 | 再提示 |
|---|------|------|------|--------|------|--------|
```

判定は `採用` / `不採用` / `ユーザー確定` / `別 issue` のいずれかとする。

### 締めの工程を確認する

ループを抜けたあとに走らせる工程（動作確認など）を指定されているかを確認する。無ければ無しとして進め、最終報告にそう書く。

**レビュー範囲が openspec の change の実装に及んでいるなら、指定が無くても `/opsx:verify` を締めに入れる。artifacts だけが対象なら入れない。** `/opsx:verify` は実装が artifacts と合っているかを見る工程で、実装が無ければ確かめる対象が無い。対象の change 名を次で拾い、台帳の冒頭に書く。

```bash
{ git status --porcelain | cut -c4-; git diff --name-only @{upstream}..HEAD 2>/dev/null; } |
  sed -n 's#^openspec/changes/\([^/]*\)/.*#\1#p' | sort -u
```

1 つならそれを採る。2 つ以上ならどれが対象かをユーザーに尋ねる。**名前を省いて `/opsx:verify` を呼ばない。** 呼ばれた側が change の選択を求めて止まる。

## 1. 待機する

**手順 0 の時点で実装が終わっているなら、待たずに手順 2 へ進む。** 完了通知を既に受け取っている場合と、`git status --porcelain` にレビュー対象の差分がある場合がこれに当たる。届かない通知を待つと、双方が相手の通知を待ったまま止まる。

そうでなければ通知を待つ。催促しない。待機に入ることを 1 行で伝えて止まる。相手がこのマシンで動いているなら `SendMessage(to: "<名前>", notify_when_idle: true)` を本文なしで送り、次に idle になったときの通知だけを購読する。相手の手は止まらない。

購読の期限切れが返ったら、相手が終了したか要求を断った可能性がある。`ListAgents` で確認し、結果をユーザーに報告して指示を仰ぐ。実装を自分で引き取らない。

## 2. code-review を 1 周回す

**この周を台帳の周回表に起こしてから回す。**

```text
Skill(skill: "code-review", args: "<effort> <PR番号>")
```

- **effort が先、ターゲットが後。** 逆にすると全体がターゲット文字列として扱われ、effort は「前回タイプしたレベルの再利用」にフォールバックする
- 作業ツリーを対象にするならターゲットを省略する。PR を対象にするなら PR 番号を明示する。code-review の既定ターゲットはローカルの upstream 設定に依存し、push 直後はコミット済み分が対象から漏れる
- `--fix` / `--comment` は付けない
- **args に指示文を足さない。** 先頭トークン以降はすべてターゲットとして扱われるため、出力形式の指定は args では渡らない。形式を揃えるのは手順 3 の受け取り側

## 3. 受け取った結果を正規化する

`code-review` の出力は揃わない。箇所や深刻度のラベルが落ちることも、日本語設定で英語が返ることもある。**受け取り側で揃えてから判定に入る。**

指摘 1 件ごとに、箇所（ファイル:行）・何が壊れるか（発動する入力か状態）・レビュアーが実際に検証したか（実行したコマンドがあるか）を持たせる。深刻度は揃わなくてよい。手順 4 の判定に使わない。

足りない項目は、その agent に `SendMessage` で聞き直す。宛先は task-notification が示した agent 名をそのまま使う。送れない場合は自分で該当箇所を確認して補い、**補ったのが自分であることを明記する。** レビュアーが検証した事実と、こちらで確認した事実を混ぜない。

英語で返ってきたら日本語に直す。要約で指摘内容を削らない。

## 4. 台帳と突き合わせる

正規化した指摘を台帳の既出行と照合し、**新規** と **既出** に分ける。照合は箇所と論点で行う。**件数はこの時点で周回表に書く。** 手順 5 以降で分岐しても記録が抜けない。

- 既出で判定済み: 台帳の判定を適用し、実装側に再送しない。**再提示は異常ではない。** レビュアーは毎周まっさらな状態から判断するので、不採用にした指摘は何周でも上がる。再提示欄を 1 増やして終わりにする
- 既出だが深刻度が前周と違う: 台帳の判定を優先する。深刻度が上がったことを理由に判定を覆すのは、レビュアーの揺れを判断に持ち込むことになる。ただし**前周に無かった根拠が新しく示されている場合は新規として扱う**（影響先のファイルや CI ジョブが新たに特定された、など）
- 新規: 手順 5 へ

新規指摘がゼロなら手順 7 へ。

## 5. 採否を判定する

新規指摘 1 件ごとに、採用・不採用・ユーザー判断に振り分けて台帳に書く。

**根拠は自分でも確認する。** レビュアーが挙げたファイル・行・ジョブは実物を読む。行番号のずれや、既に別経路で担保されている指摘が混ざる。確認せずに差し戻すと、実装側が存在しない行を探すことになる。

次のいずれかは自分で決めず、`AskUserQuestion` でユーザーに上げる。

- 修正方針が複数あり、選択で成果物が変わる（例外にするか既定値を返すか、どこで落とすか）
- 誤検知かどうか判断がつかない
- 指摘が設計判断そのものを覆す
- この変更の範囲を超える（別 issue に切るべきか）

ユーザーが決めた内容は判定者を `ユーザー確定` として記録する。以降の周で同じ指摘が上がっても再度上げない。

**`別 issue` と判定したものは、判定で終わらせない。** 起票されないまま流れると、PR を読む人には対応済みか未着手かが分からない。症状・箇所・この変更に含めない理由を添えて実装側に渡す。起票の判断と実行は実装側が持つ。渡したことを台帳に書く。

## 6. 実装側に差し戻す

**1 周につき 1 通に束ねる。** 思いついた順に小分けで送ると、実装側が何通目を反映済みか分からなくなり、こちらも訂正を送ることになる。

送る直前に `role.sh get impl` と `ListAgents` を引き直し、宛先を確かめる。**`to` には最初から `名前 [ref]` を渡す。** 名前だけで送ると、候補が 1 件でも一度は確認を求められて往復が 1 回増える。

```text
SendMessage(to: "impl [3b2b91]", summary: "<N>周目: <要旨>", message: ...)
```

本文に入れるもの。

- 何周目か、上限は何周か、修正後にまた通知が欲しいこと
- 要修正の指摘。箇所・何が壊れるか・確認した根拠・直し方。ユーザー確定のものは「ユーザー判断で確定」と明示する
- 不採用にした指摘とその理由。実装側が同じ指摘を別経路で受けたときに再検討しないで済む
- コード変更が不要で、ドキュメントだけの修正ならそう明記する

**規約に依拠する指示は、規約の原文と対象の実データを両方見てから送る。** 履歴の書き換えなら `gh api repos/<owner>/<repo>/pulls/<N>/reviews` でレビュアーが bot か他者かを確認し、判定基準は commit-workflow スキルの本文を読む。確認せずに送ると、直後に撤回することになる。

送ったあとに誤りが分かったら、**訂正であることを明示して即送る。** 次の周にまとめない。

送信後、**周回数と上限を比べる。** 上限に達していれば手順 7 へ。達していなければ手順 1 に戻る。

## 7. ループを終える

次のいずれかで終える。**どちらで終えたかを報告に書く。上限で打ち切ったことを、指摘が解消したかのように書かない。**

- 新規指摘がゼロ
- 上限周回に達した。残る指摘がすべて判定済みであることを台帳で確認する。未判定の新規指摘が残っているなら、上限に達した事実とその内容を報告して指示を仰ぐ

### 締めの工程

手順 0 で決めた締めの工程を実施する。**`/opsx:verify` を入れたなら、手順 0 で拾った名前を渡して実行する。**

結果は判定者を `opsx:verify` として台帳に起こす。CRITICAL は新規指摘として扱い、手順 6 で差し戻して手順 1 に戻る。WARNING と SUGGESTION は手順 5 の基準で採否を決める。

**tasks.md の未チェックも実装側に返す。** チェックを付けるのも実装のうちで、レビュー側はファイルを触らない。

CRITICAL が残っている間はループを終えない。上限周回に達しているなら、達した事実と残る CRITICAL を報告して指示を仰ぐ。**archive はこのスキルの範囲外なので実行しない。**

### 実環境での動作確認

**このループが確かめるのは指摘の解消までで、実環境で動くことは確かめていない。** テストが green でも、実際に動かすと落ちる経路は残る。締めとして動作確認セッション（verify）を通すかどうかを、ループを終える時点で決める。動かすコードが範囲に無いなら通さない。

- `role.sh list` に `verify` がある: 結果が届くのを待つ。既に届いているなら台帳に起こす
- いない: 立てるかどうかをユーザーに確認する。**このセッションでは実施しない。** レビュー側が実環境を触ると、実装側の作業ツリーと衝突する

**手順はリポジトリのスキルに委ねる。** 接続先 DB の実測、テストデータの用意、ポートの衝突の見分けはリポジトリごとに違う。このスキルは、動作確認を通したかどうかと、その結果の宛先だけを決める。

verify の結果は実装側に渡す。PR の動作確認の節に反映するのは実装側なので、届かないと書けない。**確認できなかった範囲とその理由も、確認できた範囲と同じ扱いで残す。**

### 最終報告

次を書く。

- 何周回して、各周の新規指摘が何件だったか
- 台帳の要約（採用・不採用・ユーザー確定・別 issue の件数）
- 締めの工程の結果。`/opsx:verify` を通したなら CRITICAL の有無、動作確認を通したならその範囲
- **マージ前に人がやる宿題。** 誰も実測していない前提が残っているなら明示する。「入っているはず」を根拠に省略しない

最終結果を 1 通送って終わる。宛先は実装側。**実装側はこれを受けてコミットと PR を作る。** 届かないと、実装側は自分の完了通知だけを根拠に進むことになる。

## 途中で対象が増えた場合

**最終報告（手順 7）を送る前か後かで扱いが変わる。**

- **送る前**: 周回カウンタをリセットしない。増えた分を台帳の別セクションに起こし、増分をレビューする。上限は元の残り周回数のまま扱い、足りなくなったらユーザーに確認する
- **送ったあと**: 前のループは閉じている。周回を 1 から数え直し、台帳に新しい周回表を作る。**残り周回数を引き継がない。** 引き継ぐと、PR 作成後の追加変更が 1 周も回らないまま上限で打ち切られる

**依頼が実装側から届いても、レビュー範囲を確定し直すのは自分の役割。** 手順 0 の「レビュー範囲を確定する」をやり直す。PR が作られたあとなので、対象の判定条件が前回と変わっている。

## 実装側の作法

**役割の登録。** 起動時に `~/.claude/skills/send-msg/role.sh set impl` を実行する。宛先は `role.sh get review` で `名前 [ref]` に解決し、`ListAgents` の行に突き合わせてから送る。同じ worktree のレビューセッションだけが相手になる。

**完了通知。** 本文には、実装した範囲、対象ファイル、通した検証（テストの実行結果、lint）を書く。「完了しました」だけではレビュー側が範囲を推測することになる。

**差し戻しへの返答。** 修正した点・方針を変えた点・反論する点を分けて書く。反論には根拠（ファイル:行、実行結果）を付ける。ドキュメントだけの修正ならコード変更が無いことを明記する。

**判断が割れたら自分で決めない。** レビュー側かユーザーに上げる。

**共有成果物に余計な差分を出さない。** 仕様・設計のドキュメントは修正が必須な箇所だけ触る。環境固有の値や手元のラッパーコマンドは書かない。往復で得た経緯は PR description に置き、ドキュメントには結論だけ残す。

**review の最終報告を受け取るまでコミットしない。** 自分の完了通知はレビュー通過を意味しない。レビューループは周回ごとに完了通知を出すので、それを合図にすると、review が次の周で差し戻す予定の差分をコミットすることになる。review が居ない worktree でレビューを省くかは、自分で決めずユーザーに確認する。

コミット前に commit-workflow スキルを読み、PR の作成と本文は pr-description スキルに従う。履歴の書き換え（amend / rebase / force push）の可否は commit-workflow の判定基準に従い、レビュー状況を実データで確認してから行う。

**動作確認の結果を PR に載せる。** verify がいるならその報告を動作確認の節に反映し、確認できていない範囲も同じ扱いで残す。書き方は pr-description に従う。

**スコープ外の気づきを引き受ける。** review が「別 issue」と判定したもの、verify や自分が気づいたものは実装側が持つ。起票は issue-description スキルに従う。PR には、既起票ならその番号を、未起票なら「未起票」と明記する。書かないと、読み手には対応済みか未着手か分からない。

**この変更で直すと決めたものは、直したうえで review の周回に載せる。** 変更である以上、レビューを通さずには入れない。

**最終報告。** 作ったもの（コミットのハッシュ、PR の URL と draft / ready、起票した issue）と、マージ前に人がやる宿題を書く。誰も実測していない前提が残っているなら明示する。

**PR 作成後の追加変更も review を通す。** 完了通知を送り直せば、レビュー側が周回を数え直して増分をレビューする。通す前に追加コミットを積まない。
