# コミット運用ルール

commit やコミット計画の分割は、レビュー・revert がしやすい単位で行う。

## コミット粒度の原則

- 1 コミット 1 つの論理的変更にする。「なぜこの変更をしたか」を 1 文で説明できる範囲を 1 コミットの目安とする。無関係な変更を 1 コミットに混ぜない。
- 各コミット単独でビルド・テストが通る状態を保つ（bisect 可能にする）。
- 挙動を変える変更とそれ以外を分ける。
  - リファクタリング（挙動を変えない整理）と機能変更・バグ修正は別コミットにする。
  - フォーマット・リネーム・自動生成物の更新など機械的な変更は、ロジック変更と別コミットにする（差分ノイズでレビューを埋もれさせない）。
- revert しやすさを優先する。ある変更だけを後から取り消したくなったときに、1 コミットの revert で完結する切り方にする。依存関係がある場合は、土台となる変更を先のコミットに置く。
- 1 つの論理的変更でも大きくレビューしづらい場合は、レビューしやすい小さめの単位に分ける。

## コミットメッセージ

**差分から読み取れることは書かない。** 変更したファイルの列挙、追加した項目やメソッドの説明、実装手順の要約は差分が語る。詳しく書くほど親切になるわけではなく、読み手が差分と突き合わせる手間が増えるだけとみなす。

書くのは差分に現れない「なぜ」に限る。

- その変更が必要になった背景・解決した問題
- 素直な書き方を採らなかった理由。検討して却下した案
- 差分に現れない事実。あえて含めなかったものとその理由、別リポジトリ・CI・運用手順への依存

「なぜ」であっても、同じコミットで変更した設計ドキュメントやコメントに書いてあるなら繰り返さない。

長さは内容で決める。書くべき「なぜ」が無ければ件名 1 行で終える。行数を埋めない。

## レビュー後は履歴を書き換えない

PR に bot 以外・作成者以外のレビューが付いた後は、そのブランチの既存コミットを書き換えない。作成者自身のレビューコメントは数えず、他者のレビューが 1 件も無ければ書き換えてよい。追加の変更は新しいコミットとして積む。書き換えるとレビュアーが見た差分が消え、レビュー後に何が変わったかを追えなくなるため。

書き換えにあたる操作をすべて対象とする。`git commit --amend`、`git rebase`（`-i` / `--onto` / `--autosquash`）、`git reset` によるやり直し、`git push --force` / `--force-with-lease`。まとめる必要があるときは merge 時の squash に任せる。

指摘への対応も通常のコミットとして積む。fixup コミットを作って後で潰す運用は取らない。

### 判定手順

作業中のブランチに PR があるかを確認する。PR が無ければこの制約は適用しない。

```bash
gh pr view --json number,author -q '"\(.number) \(.author.login)"'
```

取得した番号と作成者で、bot 以外・作成者以外のレビューを数える。

```bash
gh api repos/{owner}/{repo}/pulls/<番号>/reviews \
  --jq '[.[] | select(.user.type != "Bot" and .user.login != "<作成者>")] | map(.user.login) | unique'
```

`[]` なら書き換えてよい。1 件でも返れば書き換えない。

`user.type` は GitHub App の bot を `Bot` と返すが、個人アカウントで動く bot は `User` になる。login が明らかに bot のものはレビュアーとして数えない。

判定結果は同じブランチで作業を続ける間は使い回してよい。レビュー依頼を出した後と、セッションをまたいだ後は取り直す。

### 例外

ユーザーが書き換えを明示的に指示した場合は従う。その場合も force push の前に、どのコミットがどう変わるかを伝える。

## コミット前の検証

### 検証項目の発見（漏れを防ぐ手順）

「どの lint・test を実行すべきか」を記憶や推測で列挙しない。個別ツール名（eslint / cspell / prettier など）を思い出す方式は必ず取りこぼす。代わりに、commit の前に**リポジトリ内の権威ある定義を読み、検証項目の集合を毎回その場で列挙する**。以下を上から順に確認し、見つかったものをすべて検証項目に加える。

1. **CI 設定**（最優先・最も網羅的）: `.github/workflows/*.yml`、`.gitlab-ci.yml`、`.circleci/config.yml` 等。PR/push で走る job・step を読み、そこで実行されるチェック（lint・型・test・spell check 等）を列挙する。CI が通す条件がコミットが満たすべき条件なので、これを基準にする。
2. **pre-commit / commit フック定義**: `.pre-commit-config.yaml`、`lefthook.yml`、`.husky/`、`lint-staged` 設定（package.json / `.lintstagedrc*`）。commit 時に本来走るチェックが列挙されている。
3. **タスクランナのスクリプト**: `package.json` の `scripts`（`lint`、`lint:*`、`typecheck`、`test`、`spell*`、`check` など集約タスクを含む）、`Makefile`、`Taskfile.yml`、`justfile`、`composer.json` 等。集約タスク（例: `npm run lint` が内部で複数ツールを呼ぶ）があればそれを優先して使う。
4. 上記が存在しない場合に限り、設定ファイルの実在（`.cspell.json`、`.eslintrc*`、`ruff.toml` 等）から個別ツールを推定してよい。

列挙した項目のうち、変更内容に関連するものを漏れなく実行する。**cspell / spell check のように「関連ファイルがあれば必ず対象になる」種類のチェックは、lint の一部として扱い省略しない。** どれを実行しどれを範囲外としたかを判断できる状態にしておく。

### 実行と結果の扱い

- commit する前に、上で発見した項目のうち変更に関連する test と lint を実行し、通ることを確認してから commit する。
- 変更と無関係な全テストの実行までは必須としない。変更したファイル・モジュールに関連する test と lint に絞ってよい（範囲の判断が難しいときは広めに実行する）。ただし絞るのは「実行スコープ（対象ファイル）」であって「チェックの種類」ではない。種類は上の発見手順で列挙した集合を基準にし、恣意的に間引かない。
- test または lint が失敗したら commit しない。原因を修正して再実行するか、修正が難しい場合はユーザーに報告して指示を待つ。`--no-verify` 等での検証スキップはしない。
- 自動コミット（`CLAUDE_AUTO_COMMIT=1`）時も同様に、各コミット前に発見手順で列挙した関連 test・lint をすべて実行し、通ったコミットのみ作成する。

## コミット計画を立てるとき

- 既存の変更（作業ツリー）を複数コミットに分割する計画を立てる場合は、実行前に分割案（各コミットの対象ファイル・粒度・順序・意図）をユーザーに提示し、合意を得てから実行する。
- 適切な分割が難しい変更（例: 1 つの変更が広範囲に絡む）がある場合は、その旨と分割の選択肢をユーザーに伝える。

## 自動コミットの許可（例外）

- `CLAUDE_AUTO_COMMIT` の値が `1` のとき（未設定や `1` 以外の値は無効）は、`git commit` を作業の一環として自発的に実行してよい（提案・確認を省いてよい）。
- 値の判定は次の優先順位で行う。環境変数はセッション開始時のスナップショットなので、セッション途中で `toggle-auto-commit` により切り替わっている場合がある。
    1. UserPromptSubmit フックが `CLAUDE_AUTO_COMMIT の現在値は ...` という文脈を注入していれば、それを正とする（環境変数と食い違ったときだけ注入される）。
    2. 注入がなければ環境変数 `CLAUDE_AUTO_COMMIT` の値を使う。
    3. どちらも判断がつかないときは `toggle-auto-commit status` で現在値を確認する（設定ファイルを読むだけで、状態は変更しない）。
- 自動コミット時も上記「コミット粒度」の原則は適用する。ただし分割案の事前提示・合意取得（手動コミット時に必要なステップ）は省き、粒度原則に従って自律的に分割・コミットしてよい。適切な分割が難しい変更がある場合は、自動モードでもその旨を簡潔に申告する。
- この例外は `git commit` のみが対象。`git push` は引き続き指示待ち・確認必須とする。
