# PR description

新規作成と更新の両方に適用する。節の構成はリポジトリの PR テンプレートに従い、この skill は節の中の書き方を決める。

- テンプレートの HTML コメントは残さず消す
- テンプレートの見出しは消さない。書くことが無ければ空のまま残す。以降の「節を置かない」は、テンプレートが無い場合の話である
- レビュー期日などの日付欄は、例外なく空にする。日付が必要なときはユーザーが自分で書く

テンプレートが無ければ、次のうち必要な節だけを置く。

- `## 概要`: 解決する問題と、それが問題である理由
- `## 方針`: 採った方針と、他の案を採らなかった理由。方針が自明なら置かない
- `## 動作確認`: 確認した事実（後述）
- `## 備考`: 判断に必須ではない補足、スコープ外として切り出した課題

## 要点だけを書く

レビュワーが diff を読む前に知っておくべきことだけを書く。diff にあるものは書かない。
変更したファイルの列挙、クラスやメソッドの追加報告、実装をなぞった手順、変更の規模がこれに当たる。

description にしか書けないものが本体になる。

- 解決する問題と、それが問題である理由
- 採った方針と、他の案を採らなかった理由
- diff から読み取れない前提。外部システムの挙動、仕様上の制約、既知の不具合
- 変更したファイルの外に出る影響。移行手順、設定変更、デプロイ順序

## 書き終えたら削る

反映する前に 1 文ずつ「これが無いとレビュワーは何を誤るか」を問い、答えられない文を消す。「誤らないが親切」も消す。

次のものは本文から常に消す。

- 前置きと締め。「本 PR では」「以上です」「ご確認よろしくお願いします」
- 見出しを言い換えただけの書き出し
- 直前の文の言い換えと、末尾のまとめ
- 実行環境の固有事情。worktree のパス、ツールチェーンの起動方法、バケット名、ログイン手順、ブラウザ自動化の詰まり、ローカル DB の件数
- 検証時の内部識別子と作業語彙。ラン ID、ケース番号、シナリオ記号、「ラン」「ケース」「試行」

節が長くなったら、diff の言い換えが混ざっていないか、details に畳むべきもの（後述）が本文に出ていないかを見直す。

文と語の書き方は `~/.claude/rules/japanese-writing.md` に従う。

## body を反映する手順

本文は常にファイルに書き出して渡す。`--body` に長文を直接渡すと、改行やバッククォートがシェルで壊れる。

新規作成は `gh pr create --title <タイトル> --body-file <ファイル> --draft` で行う。**`--draft` を既定にする。** ユーザーが draft にしないと指示したときだけ外す。**ready に上げるのもユーザーの指示を受けてから。** 作成の時点では動作確認やスコープ外の起票が済んでいないことが多い。draft なら、レビュワーに通知が飛ぶ前に足せる。

更新は、skill 呼び出しでも `gh pr edit` を実行する流れでも、次の手順で行う。

1. 対象 PR を決める。引数があればそれを使い、無ければ `gh pr view --json number,url` で現在のブランチの PR を特定する
2. 直前に `gh pr view <番号> --json body -q .body` で現在の body を取得して読む。自分が直前に作成した PR でも省かない。間に他者が触れたかは分からない
3. 取得した内容の上に変更を重ねた全文を作り、ファイルに書き出す。節を差し替えるときは、取得した body から前後を切り出して新しい節を挟む。手で全文を書き写すと、触らないはずの節に差分が入る
4. 取得した body と作った全文を `diff` し、意図した節以外が変わっていないことを確認する
5. `gh pr edit <番号> --body-file <ファイル>` で反映する

手元の草案や自分が以前生成した内容で上書きしない。ユーザーやレビュワーの編集を消してしまう。他者が書いた記述は、節を作り替える場合もそのまま残し、依頼された範囲を超えて書き直さない。

既にある数値を書き換える前に、自分の測定対象が元と同じか確かめる。違うなら数だけ差し替えず、対象が変わったと読み取れる形にする。同じ「N ファイル」でも含むファイルが違えば別の測定で、数だけ動かすと読み手は前の数と突き合わせられない。

画像の添付は `~/.claude/rules/github-attachments.md` に従う。

## チケットとの関連

issue を閉じるときは [GitHub のキーワード構文](https://docs.github.com/ja/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue#linking-a-pull-request-to-an-issue-using-a-keyword)に従い、キーワードは `close` を使う。ベースブランチが既定ブランチかどうかで書き分けない。URL 形式や `close:` は使わない。

- 同じリポジトリ: `close #<番号>`
- 別リポジトリ: `close <owner>/<repo>#<番号>`
- 複数閉じるときは issue ごとにキーワードから書く（`close #10, close #12`）

`close` の行だけは箇条書きにせず、それ以外の関連情報は箇条書きにして下に並べる。ユーザストーリーの文書がある場合は先頭の項目に `US:` を置き、タイトルをリンクテキストにしたマークダウンリンクで書く。親 issue、設計ドキュメントなどはその後に続け、issue の参照は `close` と同じ形式で書く。

```markdown
close #123

- US: [ユーザーは通知の送信先を画面から変更できる](<US の URL>)
- 親 issue: #100
- 設計: `docs/design/notification-destination.md`（決定 2・3）
```

スコープ外として切り出した課題は、`close` の対象と混ぜず「備考」に置く。1 行 1 件で番号リンクにし、経緯と根拠は issue 側に書いて body には症状の 1 行だけ残す。未起票のものを書く前に、その課題が既知かユーザーに確認する。把握済みのものを新しい発見として並べると、削除の手戻りになる。

```markdown
検証中に見つけたスコープ外の課題は issue に切り出した。いずれも修正前からの挙動で、本 PR の後退ではない。

- #150 一覧画面で並び順を変えると 2 ページ目以降に同じ行が現れる
- #151 削除済みユーザーを含む期間で集計するとエラーになる
```

## 動作確認の節は確認した事実を並べる

CI の結果で分かることは書かない。spec・lint・型検査・Vitest などが通ったという報告がこれに当たる。書くのは、CI が走らない確認だけとする。画面での確認、ローカルや別環境での E2E、本番データでの突き合わせがこれに当たる。

確認した項目だけを書き、未チェックの項目は置かない。未実施で判断に関わるものは summary でユーザーに伝える。**自分以外の報告を根拠に書くときは、その報告に無い項目を確認済みとして書かない。**

確認できた挙動を 1 行 1 件の文で並べる。「入力の種類」「除外条件」のような分類名を列にした表にしない。分類名は中身を隠すので、読み手はその行で何を確かめたのか分からなくなる。表にするのは、確認した組み合わせが 2 つ以上の軸の積になるときと、修正前後の比較だけとする。修正前後は前と後を列にした表で本文に並べ、details に畳まない。スクリーンショットも同じ。

実行回数そのものは成果ではない。件数を書くなら、対象集合を特定できる形にする。ファイル数と件数だけでは、別の集合を測った数と区別が付かない。

判定方法が自明でないときは、結果ではなく方法を 1 文で添える（「バイト列の部分一致では 2 バイト文字の境界を跨いで誤検出するため、復号してから文字単位で判定した」）。

## 補足は details に畳む

レビューの判断に必須ではないが残しておきたいものは `<details>` に入れる。計測条件、テストの内訳、実行計画の確認、突合の結果、個別のログや値、実行の一覧などが該当する。再現に要る計測条件は、本文から削っても details には残す。

summary には「詳細」「補足」ではなく、畳んだ中身の主張を書く。開かなくても何が書いてあるか分かる状態にする。

```markdown
<details>
<summary>10,000 行の取り込みで実行時間が 30% 短縮した</summary>

...

</details>
```
