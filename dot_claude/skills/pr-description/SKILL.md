# PR description

新規作成と更新の両方に適用する。節の構成はリポジトリの PR テンプレートに従い、この skill は節の中の書き方を決める。テンプレートの HTML コメントは残さず消す。

テンプレートが無ければ、次のうち必要な節だけを置く。

- `## 概要`: 解決する問題と、それが問題である理由
- `## 方針`: 採った方針と、他の案を採らなかった理由。方針が自明なら置かない
- `## 見てほしい箇所`: ユーザーが pr-focus skill で指示した点の索引。指示が無ければ置かない（後述）
- `## 動作確認`: 何を覆ったかを軸で示す（後述）
- `## 備考`: 判断に必須ではない補足、スコープ外として切り出した課題

## 要点だけを書く

レビュワーが diff を読む前に知っておくべきことだけを書く。diff にあるものは書かない。
変更したファイルの列挙、クラスやメソッドの追加報告、実装をなぞった手順、変更の規模がこれに当たる。

description にしか書けないものが本体になる。

- 解決する問題と、それが問題である理由
- 採った方針と、他の案を採らなかった理由
- diff から読み取れない前提。外部システムの挙動、仕様上の制約、既知の不具合
- ユーザーが pr-focus skill で指示した、見てほしい箇所と確認してほしい観点。変更箇所に紐づくものは body ではなく diff のコメントに置く（後述）
- 変更したファイルの外に出る影響。移行手順、設定変更、デプロイ順序

1 つの節は 3〜5 行に収める。超えたときは、diff の言い換えが混ざっているか、details に畳むべき検証の詳細が本文に出ている。

## 書き終えたら削る

反映する前に 1 文ずつ「これが無いとレビュワーは何を誤るか」を問い、答えられない文を消す。「誤らないが親切」も消す。

次のものは本文から常に消す。再現に要る計測条件は消さずに details に畳む（後述）。

- 前置きと締め。「本 PR では」「以上です」「ご確認よろしくお願いします」
- 見出しを言い換えただけの書き出し
- 直前の文の言い換えと、末尾のまとめ
- 実行環境の固有事情。worktree のパス、ツールチェーンの起動方法、バケット名、ログイン手順、ブラウザ自動化の詰まり、ローカル DB の件数
- 検証時の内部識別子と作業語彙。ラン ID、ケース番号、シナリオ記号、「ラン」「ケース」「試行」

文と語の書き方は `~/.claude/rules/japanese-writing.md` に従う。

## 見てほしい箇所はユーザーの指示だけを書く

この節に書くのは、ユーザーが pr-focus skill で指示した点だけとする。自分が重要だと判断した箇所を足さない。指示が無ければ節ごと置かず、diff コメントも投稿しない。

指示の無い観点を並べると、ユーザーが見てほしいと思っていない箇所にレビュワーの注意が向く。挙げたい箇所が思い浮かんだときは、body ではなく summary で伝える。

指示された点が diff の hunk 内の行に紐づけられるなら、観点を body に書かず該当行にコメントし、body には索引だけ置く。この関数をこう変えた理由、この定数の選定、この命名のように、特定の変更箇所に紐づく判断がこれに当たる。レビュワーが本文とコードを往復しなくて済む。

紐づけられないものは body に残す。変更していない行、hunk の外、複数ファイルに跨る観点、全体の方針や他案を採らなかった理由がこれに当たる。

投稿と索引の作り方は `reference/review-comments.md` に従う。

## 更新するときは、現在の内容を確認してから重ねる

更新の直前に現在の body を取得して読む（`gh pr view <番号> --json body -q .body` など）。手元の草案や自分が以前生成した内容をそのまま上書きしてはならない。ユーザーやレビュワーが編集している場合があり、その編集を消してしまう。

変更は現在の内容の上に重ねる。節を作り替える場合も、他者が書いた記述はそのまま残す。表現を整えたい箇所があっても、依頼された変更の範囲を超えて他者の文章を書き直さない。

自分が直前に作成した PR であっても確認する。作成からの経過時間ではなく、間に他者が触れた可能性の有無は分からないという前提で扱う。

既にある数値を書き換える前に、自分の測定対象が元と同じか確かめる。違うなら数だけ差し替えず、対象が変わったと読み取れる形にする。同じ「N ファイル」でも含むファイルが違えば別の測定で、数だけ動かすと読み手は前の数と突き合わせられない。

見てほしい箇所の節は、その更新で pr-focus skill による指示を受けたときだけ作る・書き換える。指示が無ければ、既にある節はそのまま残し、新しく足さない。

## body を反映する手順

skill 呼び出しでも、`gh pr edit` を実行する流れでも、更新は次の手順で行う。

1. 対象 PR を決める。引数があればそれを使い、無ければ `gh pr view --json number,url` で現在のブランチの PR を特定する
2. `gh pr view <番号> --json body -q .body` で現在の body を取得して読む
3. 取得した内容の上に変更を重ねた全文を作り、ファイルに書き出す
4. 取得した body と作った全文を `diff` し、意図した節以外が変わっていないことを確認する
5. `gh pr edit <番号> --body-file <ファイル>` で反映する

節を差し替えるときは、取得した body から前後を切り出して新しい節を挟む形で組み立てる。手で全文を書き写すと、触らないはずの節に差分が入る。

新規作成も本文はファイルに書き出し、`gh pr create --title <タイトル> --body-file <ファイル> --draft` で作る。`--body` に長文を直接渡さない。改行やバッククォートがシェルで壊れるのを避けるため。

**`--draft` を既定にする。** ユーザーが draft にしないと指示したときだけ外す。**ready に上げるのもユーザーの指示を受けてから。** 作成の時点では動作確認やスコープ外の起票が済んでいないことが多い。draft なら、レビュワーに通知が飛ぶ前に足せる。

## チケットとの関連

issue を閉じるときは [GitHub のキーワード構文](https://docs.github.com/ja/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue#linking-a-pull-request-to-an-issue-using-a-keyword)に従う。キーワードは `close` を使う。

- 同じリポジトリ: `close #<番号>`
- 別リポジトリ: `close <owner>/<repo>#<番号>`
- 複数閉じるときは issue ごとにキーワードから書く（`close #10, close #12`）

URL 形式や `close:` は使わない。

ベースブランチが既定ブランチでない PR ではキーワードが無視され、リンクは作られない。この場合は `close` を書かず `関連: #<番号>` として並べ、issue は merge 後に手で閉じる。

`close` の行だけは箇条書きにしない。それ以外の関連情報は箇条書きにして `close` の下に並べる。

ユーザストーリーの文書がある場合は、先頭の項目に `US:` を置く。タイトルをリンクテキストにしたマークダウンリンクで書く。親 issue、設計ドキュメントなど他に示すものがあればその後に続ける。issue の参照は `close` と同じ形式で書く。

```markdown
close #123

- US: [ユーザーは通知の送信先を画面から変更できる](<US の URL>)
- 親 issue: #100
- 設計: `docs/design/notification-destination.md`（決定 2・3）
```

スコープ外として切り出した課題は、`close` の対象と混ぜず「備考」に置く。1 行 1 件で番号リンクにし、経緯と根拠は issue 側に書いて body には症状の 1 行だけ残す。

```markdown
検証中に見つけたスコープ外の課題は issue に切り出した。いずれも修正前からの挙動で、本 PR の後退ではない。

- #150 一覧画面で並び順を変えると 2 ページ目以降に同じ行が現れる
- #151 削除済みユーザーを含む期間で集計するとエラーになる
```

## 期日の欄は空のままにする

テンプレートにレビュー期日などの日付欄があれば、例外なく空のままにする。日付が必要なときはユーザーが自分で書く。

## 動作確認の節は軸で書く

本文には、何を覆ったかを軸で示す。経路・入力・条件・エラー種別のように、レビュワーが「抜けている組み合わせはないか」を数えられる形にする。個別のログや値、実行の一覧は details に畳む。

表の行も本文からの参照も、内容で識別する。実行回数そのものは成果ではない。数を書くなら、表の行数など読み手が確かめられるものと対応させる。

**未実施の範囲とその理由も残す。** 「ジョブ層のみ確認、画面経由の E2E は未実施」のように、何が確認できていないかを読み手が数えられる形にする。**自分以外の報告を根拠に書くときは、その報告に無い項目を確認済みとして書かない。**

判定方法が自明でないときは、結果ではなく方法を 1 文で添える（「バイト列の部分一致では 2 バイト文字の境界を跨いで誤検出するため、復号してから文字単位で判定した」）。

## 補足は details に畳む

動作確認・検証の内容のうち、レビューの判断に必須ではないが残しておきたいものは `<details>` に入れる。計測条件、テストの内訳、実行計画の確認、突合の結果などが該当する。

summary には「詳細」「補足」ではなく、畳んだ中身の主張を書く。開かなくても何が書いてあるか分かる状態にする。

```markdown
<details>
<summary>10,000 行の取り込みで実行時間が 30% 短縮した</summary>

...

</details>
```
