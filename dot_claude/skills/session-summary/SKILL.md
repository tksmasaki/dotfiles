# Session Summary

現在のClaude Codeセッションの内容を要約したMarkdownファイルを書き出すskill。

単なる「やったことの羅列」ではなく、**後から自分や他人がセッションを再構築できる程度の文脈（why）を残す**ことが目的。

## 出力先・ファイル作成

出力先の決定とディレクトリ作成は、Skill ツールで `md-output` を起動し、そのルールに従う（この skill 独自の出力先・引数は持たない）。

## ファイル名の決め方

毎回、そのセッション内容に合ったケバブケースのトピックスラッグをファイル名にする。

形式: `<kebab-case-topic>.md`

良い例:
- `user-settings-page-implementation.md`
- `login-flow-bug-investigation.md`
- `data-table-component-refactor.md`

避けるべき例（汎用的すぎる）:
- `work.md`
- `session.md`
- `notes.md`

トピックスラッグは2〜5語程度で、何のセッションだったか後から見て即座に判別できるようにする。

## ファイル内容のテンプレート

以下のセクション構成で書く。**該当する内容がないセクションは省略する**（無理に埋めると読みづらくなる）。

```markdown
# <セッションタイトル>

- 日時: YYYY-MM-DD HH:MM
- 関連リポジトリ: <repo名 または「なし」>

## 概要

2〜4文で「何を達成したか／何を議論したか」を書く。

## やったこと

時系列または論理順に箇条書き。実際に行った操作・実装・調査を具体的に書く。
ファイルパスは、行が特定できる場合は `file:line` 形式で、ファイル全体や行に紐づかない変更は file パスのみで書く。
作業の再現に必要なコマンド（セットアップ・ビルド・マイグレーション・特定の検証手順など）は、その**コマンド自体を記載する**。再現に不要な一度きりの確認・閲覧コマンドは省く。コマンドに認証情報・機密（トークン・パスワード・接続文字列など）が含まれる場合は、該当部分をプレースホルダ化して記載する。コマンドが長い・複数行にわたる場合は、折りたたみ（md-output skill の `<details>` 方式）で記載する。

## 判断の理由・トレードオフ

なぜその選択をしたか、検討した代替案、却下した理由。
コードや設定からは読み取れない why を残すのがここの主目的。

## 起きた問題と対処

エラー・想定外の挙動・行き詰まりと、それをどう解決または回避したか。
未解決なら「未解決事項」に回す。

## ユーザーからの指示・フィードバック

セッション中にユーザーから受けた重要な指示・訂正・好み。
特に「やめて」「こうして」系の指示は引用して残す。

## 未解決事項・次のステップ

TODO、宿題、後で対応すべきこと。
次回セッション再開時の起点になる情報。
```

## 書き出し手順

1. これまでのセッション内容（ユーザー発言・ツール呼び出し・結果を含む全体）を振り返り、上記テンプレートに沿った内容を組み立てる
2. ファイル名用のトピックスラッグを決める
3. Skill ツールで `md-output` を起動し、その出力先決定ルールに従って保存先を決める（ディレクトリは `mkdir -p` で作成）
4. 内容の「日時」欄は `date +"%Y-%m-%d %H:%M"` で取得する
5. 同名ファイルが既に存在する場合は `<topic>-2.md`・`<topic>-3.md` のように連番サフィックスを付ける
6. Write tool で絶対パス指定でファイルを書き出す
7. 保存先の報告は md-output skill のルールに従う（保存先の絶対パス + 1行サマリ）

## 守ること

- **機密情報を含めない**: APIキー、パスワード、トークン、個人情報など。会話に出てきても要約には書かない
- **why を省かない**: コードや設定からは読み取れない判断の文脈を必ず残す
- **嘘を書かない**: セッション中に実際に発生したことだけ書く。やっていないことを「やったこと」に書かない
- **冗長な前置きを避ける**: ファイル冒頭に「このドキュメントは……」のような自己言及は不要
- **再構築しにくい詳細は正確に残す**: 名前・数値・日付・リンク・参照先・決定や制約の文言は言い換えず、そのまま書く
- **二つの声の重みを分ける**: ユーザーが言ったこと・求めたこと・決めたことは原文に近く残す。自分の説明や推論は、結論と成果物まで圧縮してよい
