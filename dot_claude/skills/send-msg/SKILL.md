# 別セッションへ送る

## 経路を選ぶ

宛先の指定方法が経路ごとに違うので、先にどちらかを確定する。

```bash
printf '%s\n' "${CLAUDE_CODE_ENTRYPOINT:-cli}"
```

`claude-desktop` ならデスクトップ経路、それ以外は CLI 経路に進む。デスクトップアプリの Code タブは起動時に `SendMessage` を無効化しているため、`No such tool available: SendMessage` が返った場合も同じ判定とする。

どちらの経路でも、自分がまだ役割ファイルに載っていなければ登録する。相手がこのセッションを役割名で引けるようになる。

```bash
~/.claude/skills/send-msg/role.sh ensure
```

自分のセッション名をそのまま役割名にする。登録したときだけ `役割<TAB>名前` を 1 行返す。既に何かの役割で載っているとき、git リポジトリの外にいるとき、名前に英数字・ハイフン・アンダースコア以外が含まれるときは何もせずに終わる。別の役割名で登録したいときは `role.sh set <役割>` を使う。

## CLI 経路

### 1. 候補を集める

`ListAgents` を 1 回呼ぶ。冒頭の `This session is <名前> [<ref>]` が自分、続く行が生きている相手。手順 2 でも同じ結果を使う。呼び直さない。

`ListAgents` は作業ディレクトリを返さない。同じ作業ツリーの相手はローカルのセッション情報から引く。

```bash
~/.claude/skills/send-msg/peers.sh
```

出力は 1 行 1 セッションのタブ区切りで、`self|same|other`・名前・`ref`・状態・作業ディレクトリ・入口（`cli|claude-desktop`）。`same` が自分と同じ作業ツリー。`--all` で他の作業ツリーも出る。

**この出力だけを根拠に送らない。** Claude Code の内部状態から組み立てているので、版が変われば黙って形が変わる。`名前 [ref]` の組が `ListAgents` の行と一致したときだけ宛先にできる。

### 2. 宛先を確定する

宛先名は `-t` の値とする。`-t` が無いときは、引数の 1 語目か依頼文で名指しされた名前（「impl に送って」の `impl`）を候補にし、手順 1 で集めた名前か役割ファイルの役割名に一致したときだけ宛先名として採る。引数の 1 語目を採ったときは残りをすべて本文とする。一致しなければ宛先名は指定されていないものとする。

宛先名が役割名（`impl` / `review` / `verify` など）なら、先に役割ファイルから引く。

```bash
~/.claude/skills/send-msg/role.sh get <役割>
```

`名前 [ref]` を 1 行で返す。解決できないときは理由を出して非ゼロで終わるので、そのまま次の段に進む。役割の割り当て全体は `role.sh list`（役割・名前・`ref`・`self|same|not-in-worktree`・状態）で見る。**この出力も `peers.sh` と同じ扱いで、`ListAgents` の行と一致したときだけ宛先にできる。**

役割名でないとき、または役割ファイルから引けなかったときは、宛先名を次の順で解決する。**どの段でも推測で送らず、ソケットパスの直接指定にも逃げない。** 受け取ったメッセージに差出人のソケットパスが載っていても、それを宛先に使わない。作業ツリーを確認せずに送ることになる。

1. `same` の行のうち名前が一致し、その `名前 [ref]` が `ListAgents` にもあるものを取る。**1 件ならそれを宛先にする。** 作業ツリーはここで確定する
2. 2 件以上なら `AskUserQuestion` で `ref` と状態を並べて選んでもらう
3. 0 件なら `--all` と `ListAgents` を見る。他の作業ツリーやクラウドに同名がいるなら、**同じ作業ツリーにはいないことを明示して**、その場所を示し、送ってよいか尋ねる。cloud は受け取るが返信できないので返事を待たない
4. どこにも無ければ、その名前のセッションは動いていない。そう伝えて終わる

`peers.sh` が何も返さないときは手順 3 から始める。作業ツリーは確認できていない。

宛先名が指定されていない場合は `same` の行を候補として挙げ、どれに送るかを尋ねる。

### 3. 送る

```text
SendMessage(to: "<宛先>", summary: "<5〜10 語のラベル>", message: "<本文>")
```

**宛先は最初から `名前 [ref]` の形で渡す。** 候補が 1 件でも、名前だけで送ると一度は確認を求められて往復が 1 回増える。`ref` は手順 2 で既に手元にある。

それでも「Not sent」で返ってきたら、エラーが示した `ref` を付けて送り直す。使うのはエラーに出た `ref` だけとする。

## デスクトップ経路

宛先を `sessionId` で指定する。CLI 経路の `名前 [ref]`・役割ファイルの役割名・ソケットパスはどれもここでは宛先にならない。

### 1. セッション一覧から候補を集める

`mcp__ccd_session_mgmt__list_sessions` を 1 回呼ぶ。1 件が 1 セッションで、`sessionId`・`title`・`cwd`・`lastActivityAt` が返る。

作業ツリーは `cwd` で絞る。

```bash
git rev-parse --show-toplevel
```

自分の作業ツリーを引き、`cwd` がここと一致するか下にある候補だけを残す。判断が付かない `cwd` は `git -C <cwd> rev-parse --show-toplevel` で引き直す。

**この一覧は生存確認ではない。** 動いていないセッションも `lastActivityAt` が古いまま並ぶ。`isRunning` もそのセッションが今ターンを処理中かどうかで、生きているかどうかではない。

### 2. title で宛先を確定する

宛先名の決め方は CLI 経路の手順 2 と同じ。照合先が `title` になる。

1. `cwd` で絞った候補のうち `title` が一致するものを取る。**1 件ならそれを宛先にする**
2. 2 件以上、または `lastActivityAt` が古くて同じセッションか判断が付かないときは、`AskUserQuestion` で `title` と `lastActivityAt` を並べて選んでもらう
3. 0 件なら `peers.sh` を見る。`same` にその名前があり入口が `cli` なら、相手はターミナルのセッションで、この経路からは届かない。そう伝えて終わる
4. 入口が `claude-desktop` なら、同じ作業ツリーで動いているが `title` が違う。`cwd` が一致する候補を `AskUserQuestion` で挙げて選んでもらう
5. `list_sessions` にも `peers.sh` にも無ければ、その名前のセッションは動いていない。そう伝えて終わる

**`title` が一致しないものを近さで選ばない。** ListAgents の名前（`chezmoi-6a` のような自動命名）や役割名は `title` と別に付くので、一致しないことは相手が別人であることを意味しない。判断が付かないなら 2 に落とす。

### 3. session_id で送る

```text
mcp__ccd_session_mgmt__send_message(session_id: "<sessionId>", message: "<本文>")
```

`summary` に相当する引数は無く、差出人はこのセッションの `title` として相手に表示される。

結果は `delivered`（相手のターンが始まった）か `queued`（今の作業の後に届く）。それ以外はエラーなので、文面をそのまま利用者に返して送り直さない。

### この経路から届かない宛先

`sessionId` で指定するため、`list_sessions` に出ない相手には届かない。別マシンの Remote Control のピアのように一覧に無いものは宛先にできない。迂回路は無いので、届かないことを利用者に返す。

- サブエージェント。`agentId` しか持たない
- ターミナルのセッション。入口が `cli` のものは一覧に出ない
- スケジュール実行・リモート起動の無人セッション。こちらから送れず、相手からも届かない

無効化されているのは送信側だけなので、CLI 経路のセッションからこのセッションへは届く。相手に役割名で引かせたいときは、経路を選ぶ段の `role.sh ensure` を済ませておく。

## 送るときの共通の約束

**1 行目を自己完結した文にする。** 受け手の人間には最初の 1 行だけがプレビューされる。挨拶や宛名から始めない。

**本文は確認を取らずに送る。** ユーザーが渡した文はそのまま、会話の要約や調査結果をこちらで組み立てた場合もそのまま送る。

送る前に聞くのは、何を送るか決められないときだけ。指示が複数の解釈を許すとき、送る内容が会話の中に見当たらないときに限る。**書いた文が妥当かどうかを確かめるためには聞かない。**

相手が処理中でも送ってよい。メッセージは次のツール実行時に届く。催促で二重に送らない。

送信後の報告は 1 行。宛先と、作業ツリーを確認できたかどうかを書く。

## 権限の越境をしない

**自分のセッションで拒否・制限された操作を相手に代行させない。** 権限はセッションごとに決まっているので、相手に回すのは利用者の判断を迂回することになる。できなかったことは利用者に返す。
