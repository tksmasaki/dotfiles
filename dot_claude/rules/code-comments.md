# コードコメント

コメントは書かない。名前と構造で表現する。

例外は次の 2 つだけとする。

- 素直な書き方を避けた理由。そうしないと何が壊れるか
- コードの外にある制約。仕様上の要請、外部システムの挙動、既知の不具合

例外に当たると思ったときも、名前を直して消せないかを先に試す。変数名・関数名の変更、定数の抽出、メソッドの切り出し、型の導入、例外メッセージやログの文言で消えるなら、コメントではなく名前の問題として扱う。「名前が説明的でないからコメントで補う」は名前を直していないだけとみなす。

名前で消せない場合も、次を確かめる。1 つでも当てはまったら書かない。

- 言語・フレームワークの標準的な挙動で説明がつく（トランザクションとロールバック、例外の伝播、遅延評価など）。読み手に前提知識が要ることは理由にならない
- 守りたい挙動を検証するテストがある。挙動はテストで守り、コメントで守らない。テスト名から何が壊れるか読めないなら、テスト名を直す
- 「コードの外にある制約」だと思うのに、参照先を 1 つも挙げられない

1 つの変更で 3 行以上のコメントを足しているときは、コメントを削るのではなく設計と命名を疑う。

例外として書く場合も、背景は PR description に置き、コメントには結論だけ残す。「コードの外にある制約」では、参照先（issue 番号・ファイルパス）を 1 つだけコメントに残す。

公開 API の doc コメントなど、ツールや規約が要求するものはこの規則の対象外。

## 例外に見えて例外でないもの

- コードを読めば分かること
- 名前を言い換えただけの説明
- 変更の経緯。git が持っている
- ある時点のデータに依存する数値。陳腐化するため構造で表す
- 計測値。PR description に日付とともに残す
