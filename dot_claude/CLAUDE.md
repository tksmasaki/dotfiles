# ユーザーグローバル設定

## md ファイル出力先

### 出力先の決定ルール

「md ファイルに出して」などの指示があった場合、以下のルールで出力先を決定する。

#### auto mode の場合（確認なし）

1. セッション中に出力先が指定済みであれば、その出力先を使う
2. git ブランチ名が `<prefix>/<branch-name>` の形式（例: `feature/123-add-new-feature`）であれば、prefix を除いたブランチ名を抽出して `~/Documents/vault/<branch-name>/` に出力する
   - branch-name の抽出: `git rev-parse --abbrev-ref HEAD | sed 's|^[^/]*/||'`
   - `main` ブランチや `/` を含まないブランチはデフォルトを使う
3. それ以外は `~/Documents/vault/`（デフォルト）に出力する

#### 通常モードの場合

- **セッション初回の md 出力時**は、出力先をユーザーに選択させる（`AskUserQuestion` ツールを使う）：
  - `default` - `~/Documents/vault/`
  - ブランチ名フォルダ - git ブランチが `<prefix>/<branch-name>` 形式なら `~/Documents/vault/<branch-name>/`（該当しない場合はこの選択肢を出さない）
  - 直接入力
- 選択した出力先を**セッション中のデフォルト出力先**として記憶し、2回目以降は確認なしで使用する
- **出力先の変更指示**（「今後は〜に出して」など）があった場合は、記憶しているデフォルト出力先を更新し、それ以降はその出力先を使う

出力先ディレクトリは `mkdir -p` で作成してから書き出す。

ファイル名は出力内容を表す kebab-case にする。

### md ファイルへのメタデータ記載

md ファイルに出力する際は、ファイル末尾に以下のメタデータセクションを必ず付与する：

```
---
- model: <使用したモデルID（例: claude-sonnet-4-6[1m]）>
- effort: <effort レベル（例: low / medium / high / xhigh / max）>
- date: <出力日 YYYY-MM-DD>
```

- model: セッションで使用しているモデルID をそのまま記載する
- effort: `/effort` で設定した effort レベルをそのまま記載する（未設定の場合は省略）
- date: 出力時点の日付

### md ファイル出力済みの場合の要約

内容を md ファイルに出力した場合、チャット上では**保存先の絶対パス + 1行サマリ**に留める。ファイルに書いた内容を本文で再掲しない（トークン節約のため）。

例:
```
保存しました: ~/Documents/vault/issues/123-add-new-feature/xxx.md
（調査対象16件中、条件に該当する4件を特定）
```

### md ファイルでの折りたたみ記載

md ファイルで折りたたみ（開閉ブロック）を書くときは、Obsidian と GitHub の両方で動く「空行区切りの `<details>` 方式」を使う。

```html
<details>
<summary>タイトル</summary>

ここに本文。空行を 1 つ入れるのが最重要。

- リスト項目
- リスト項目

</details>
```

- `<summary>` の直後と `</details>` の直前に**空行**を入れる。

## 出力テキストの文字種

ターミナル・チャット上での出力（説明文・箇条書き・見出しなど）では、以下の文字種に限定する。

**使ってよい文字種**
- ASCII 英数字・記号（`a-z A-Z 0-9 ! # - * > |` など）
- ひらがな・カタカナ
- 常用漢字
- 句読点（`、。`）・括弧（`（）「」`）

**避ける文字種（代替案）**

| 避ける文字 | 例 | 代替 |
|---|---|---|
| 丸数字 | ①②③ | `1.` `(1)` |
| プライム記号 | ′″ | 省略するか言葉で表現 |
| 囲み文字 | ㈱㊙ | 省略するか言葉で表現 |
| 全角記号 | ～－｜ | 半角 `~` `-` `\|` |
| 絵文字 | ✅❌🔍 | `[x]` `[ ]` など |
| 特殊矢印 | ⇒⟹ | `->` `=>` |

## 使用したコマンドの記載

ドキュメント等に「使用したコマンドを記載して」と依頼された場合は、特に指定がない限り **`等` や `...` で省略せず、実行した／対象となるコマンド・リソースを全て列挙**する。

- 例: `bin/rails routes -g <resource>` を複数リソースに使った場合、「等、リソースごとに」とまとめず、検索した全リソースを1行ずつ列挙する（各行にコメントで対応内容を添えると尚良い）。
- 省略してよいのはユーザーが明示的に許可した場合のみ。
- 理由: 省略すると読者が実際の調査範囲を再現・検証できず、網羅性が伝わらない。

## git の除外設定

ファイルやディレクトリを git の管理対象外にする場合、`.gitignore` でなく `.git/info/exclude` に追加することを優先する。

- `.gitignore` はリポジトリにコミットされ他の開発者に影響するため、個人的なローカル除外には使わない
- ユーザーから明示的に「gitignore に追加して」と指示された場合のみ `.gitignore` を編集する

## 例示のルール

説明・ドキュメント・設定ファイルなどで例を示す際は、特定のタスク・機能・調査内容を示唆しない抽象的な表現にする。

- ブランチ名、ファイル名、サマリ文など、あらゆる例に適用する
- 業務上の特定機能名、バグ内容、調査結果などを例に使わない
- プレースホルダー（`<description>`）や汎用的な語（`add-new-feature`、`fix-bug`）を使う

## URL を根拠とする条件

URL の内容を実際に取得・読み取れた場合のみ、その内容を回答の根拠として使う。

- 取得できていない URL の内容をもとに回答してはならない。読めていないものを読んだかのように扱うのは嘘になる。
- 取得に失敗した場合は、その URL の内容には言及せず、取得できなかった旨を伝える。

## git commit / git push の扱い

- `git commit` と `git push` は、ユーザーが明示的に指示するまで実行しない。
- コミット・プッシュを自発的に提案しない（「コミットしましょうか？」「push しますか？」等を含め、こちらから持ちかけない）。実装や修正が一段落しても、コミット・プッシュはユーザーの指示を待つ。
- ユーザーから明示的な指示があった場合のみ、コミット・プッシュを実行・提案する。

### コミット粒度

コミットを実行するとき、またはコミット計画（どの変更をどう分けてコミットするか）を立てるときは、**動作確認・レビュー・revert がしやすい単位**で分割する。具体的には次の原則に従う。

- **1 コミット 1 つの論理的変更にする。** 「なぜこの変更をしたか」を 1 文で説明できる範囲を 1 コミットの目安とする。無関係な変更を 1 コミットに混ぜない。
- **各コミット単独でビルド・テストが通る状態を保つ（bisect 可能にする）。** 「途中の壊れた状態」をコミットに残さない。これにより `git bisect` や単体 revert が機能する。
- **挙動を変える変更とそれ以外を分ける。**
  - リファクタリング（挙動を変えない整理）と機能変更・バグ修正は別コミットにする。
  - フォーマット・リネーム・自動生成物の更新など機械的な変更は、ロジック変更と別コミットにする（差分ノイズでレビューを埋もれさせない）。
- **revert しやすさを優先する。** ある変更だけを後から取り消したくなったときに、1 コミットの revert で完結する切り方にする。依存関係がある場合は、土台となる変更を先のコミットに置く。
- **粒度は「小さすぎず大きすぎず」。** レビューしやすいよう小さく保ちつつ、それ単独で意味が完結する（中途半端に機能の半分だけ、にならない）大きさにする。
- **コミットメッセージは「何を」だけでなく「なぜ」を書く。** 差分を見れば分かる内容の説明より、変更の意図・背景を残す。

#### コミット計画を立てるとき

- 既存の変更（作業ツリー）を複数コミットに分割する計画を立てる場合は、**実行前に分割案（各コミットの対象ファイル・粒度・順序・意図）をユーザーに提示**し、合意を得てから実行する。
- 上記の原則に照らして適切な分割が難しい変更（例: 1 つの変更が広範囲に絡む）がある場合は、その旨と分割の選択肢をユーザーに伝える。

### 例外: 自動コミットの許可

- 環境変数 `CLAUDE_AUTO_COMMIT=1` が設定されている場合は、`git commit` を作業の一環として自発的に実行してよい（提案・確認を省いてよい）。
- 自動コミット時も上記「コミット粒度」の原則は適用する。ただし `#### コミット計画を立てるとき` の分割案の事前提示・合意取得は省き、粒度原則に従って自律的に分割・コミットしてよい（事前提示が必要なのは手動コミット時のみ）。なお、適切な分割が難しい変更がある場合は、自動モードでもその旨を簡潔に申告する（安全弁は維持する）。
- この例外は `git commit` のみが対象。`git push` は引き続き指示待ち・確認必須とする。
- フック側も同じ環境変数で連動し、commit のみ確認プロンプトを省く（push 等が混在する場合は確認を維持する）。
