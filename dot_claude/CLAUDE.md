# ユーザーグローバル設定

文章・コメント・記号の書き方といった分量のあるルールは `~/.claude/rules/*.md` に分けてある。このファイルには短い判断基準だけを置く。

## URL を根拠とする条件

URL の内容を実際に取得・読み取れた場合のみ、その内容を回答の根拠として使う。

- 取得できていない URL の内容をもとに回答してはならない。読めていないものを読んだかのように扱うのは嘘になる。
- 取得に失敗した場合は、その URL の内容には言及せず、取得できなかった旨を伝える。
- 名前を知っていることと現状を知っていることは別。AI モデル・開発ツールなど変化の速い領域の名前は、ユーザーが書いた表記のまま検索してから答える。

## 環境依存の情報を共有成果物に書かない

commit・push される成果物（PR / issue 本文、コミットメッセージ、openspec の change、docs、コード）に、自分の環境でしか成立しない情報を書かない。読み手が再現できない手順になる。

- 個人のラッパーコマンド・エイリアス（`CLAUDE.local.md` や `~/.local/bin` で定義したもの）
- 絶対パス（`/Users/<自分>/...`）、ホスト名、ポート番号、worktree 名
- 手元だけの環境変数・設定ファイルの値

道具ではなく目的を書く。手元のラッパーコマンド名を挙げず、「対象 spec を実行して green にする」のように達成したい状態で書く。手元の実行方法は `CLAUDE.local.md` 側に置く。既存の成果物に前例があっても、それを根拠にしない。

## 変更とテストを依頼範囲に留める

作業中に既存のバグ・性能の懸念・依頼に無い挙動を見つけても、依頼された挙動がそれ無しで動かない場合を除き、この変更では直さず summary で follow-up として報告する。依頼が曖昧なときは 1 つの読み方を選んで前提を summary に書き、複数の読み方に対応する実装をしない。

テストを commit するのは依頼がある場合か、リポジトリが同種の変更にテストを持っている場合だけ。粒度は隣接するテストファイルに合わせ、動作確認用の scratch をそのまま永続テストにしない。

これは余分を足さない話であり、依頼された挙動はすべて完全に実装する。

## Bash では cd せず絶対パスで指定する

`cd <dir> && grep ...` のように移動してから相対パスを読まない。読み取り対象は `grep -rn foo /abs/path/app` のように絶対パスで書き、読み取りだけなら Grep / Read ツールを使う。

- サブエージェントに調査を依頼するときは、対象ディレクトリの絶対パスを prompt に書く。
- `cd` はそのディレクトリで動かす前提のコマンド（`bundle exec`、`git`、`npm` など）に限る。

## 思考は英語

推論・内部思考は英語で行う。

## PR / issue 本文の更新

既存 PR の body を更新する前に pr-description skill を、既存 issue の body を更新する前に issue-description skill を読む。`gh pr edit --body` / `gh issue edit --body` でも MCP の `update_pull_request` / `issue_write` でも同じ。

## コミット履歴の書き換え

`git commit --amend` / `git rebase` / `git reset` / force push を実行する前に commit-workflow skill を読む。bot 以外・作成者以外のレビューが付いた PR のブランチでは履歴を書き換えず、新しいコミットを積む。作成者自身のレビューコメントは数えない。
