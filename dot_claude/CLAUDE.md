# ユーザーグローバル設定

文章・コメント・記号の書き方といった分量のあるルールは `~/.claude/rules/*.md` に分けてある。このファイルには短い判断基準だけを置く。

## URL を根拠とする条件

URL の内容を実際に取得・読み取れた場合のみ、その内容を回答の根拠として使う。読めていないものを読んだかのように扱うのは嘘になる。

- 取得に失敗した場合は、その URL の内容には言及せず、取得できなかった旨を伝える。
- 名前を知っていることと現状を知っていることは別。AI モデル・開発ツールなど変化の速い領域の名前は、ユーザーが書いた表記のまま検索してから答える。

## 環境依存の情報を共有成果物に書かない

commit・push される成果物（PR / issue 本文、コミットメッセージ、docs、コード）に、自分の環境でしか成立しない情報を書かない。読み手が再現できない手順になる。

- 個人のラッパーコマンド・エイリアス
- 絶対パス、ホスト名、ポート番号、worktree 名
- 手元だけの環境変数・設定ファイルの値
- Claude のセッション・アーティファクトの URL やパス。チャットや外部サービスに貼る文も同じ扱い

道具ではなく目的を書く。手元のラッパーコマンド名を挙げず、「対象 spec を実行して green にする」のように達成したい状態で書く。手元の実行方法は `CLAUDE.local.md` 側に置く。既存の成果物に前例があっても、それを根拠にしない。

## 変更とテストを依頼範囲に留める

作業中に既存のバグ・性能の懸念・依頼に無い挙動を見つけても、依頼された挙動がそれ無しで動かない場合を除き、この変更では直さず summary で follow-up として報告する。依頼が曖昧なときは 1 つの読み方を選んで前提を summary に書き、複数の読み方に対応する実装をしない。

ドキュメント・spec・設定・README も同じ。依頼の実現に必須でない行（整形、言い換え、補足の追加、既存行の訂正）は触らない。一括の置換や整形をしたあとは diff を読み、意図しない変更が混ざっていないことを確かめてから報告する。

テストを commit するのは依頼がある場合か、リポジトリが同種の変更にテストを持っている場合だけ。粒度は隣接するテストファイルに合わせ、動作確認用の scratch をそのまま永続テストにしない。

上位層のテストは、下位層のテストが固定した規則を再検証しない。上位層で見るのは層をまたぐ配線（解決した値の受け渡し、永続化、発報）に限る。同じ規則を 2 層で見ると、規則を変えるときに落ちるテストが増えるだけで、守られる内容は増えない。

これは余分を足さない話であり、依頼された挙動はすべて完全に実装する。

## 既存ファイルを更新する前に現在の内容を読む

自分が前に書いた内容や手元の草案を元に上書きしない。ユーザーや他者が編集している場合があり、その編集を消す。実物が記憶と違っていれば、差分はユーザーの編集として残し、依頼された変更だけを重ねる。外部サービス上のページも同じ。

## Bash では cd せず絶対パスで指定する

`cd <dir> && grep ...` のように移動してから相対パスを読まない。読み取り対象は `grep -rn foo /abs/path/app` のように絶対パスで書き、読み取りだけなら Grep / Read ツールを使う。

- サブエージェントに調査を依頼するときは、対象ディレクトリの絶対パスを prompt に書く。
- `cd` はそのディレクトリで動かす前提のコマンド（ビルド・テスト・git など）に限る。

## 思考は英語

推論・内部思考は英語で行う。

## skill が理由で止まるとき

skill の指示が原因で確認を求めたり作業を止めたりするときは、どの SKILL.md のどの記述が根拠かを引用して示す。
