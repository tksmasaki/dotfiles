# ユーザーグローバル設定

## md ファイル出力先

「md ファイルに出して」などの指示があった場合は、以下の優先順位で出力先を決定する：

1. git ブランチ名が `<prefix>/<branch-name>` の形式（例: `feature/123-add-new-feature`）であれば、prefix を除いたブランチ名を抽出して `~/Documents/vault/issues/<branch-name>/` に出力する
   - branch-name の抽出: `git rev-parse --abbrev-ref HEAD | sed 's|^[^/]*/||'`
   - `main` ブランチや `/` を含まないブランチはデフォルトを使う
2. それ以外は `~/Documents/vault/claude-logs/`（デフォルト）に出力する

出力先ディレクトリは `mkdir -p` で作成してから書き出す。

ファイル名は出力内容を表す kebab-case にする。

### md ファイルへのメタデータ記載

md ファイルに出力する際は、ファイル末尾に以下のメタデータセクションを必ず付与する：

```
---
- model: <使用したモデルID（例: claude-sonnet-4-6[1m]）>
- effort: <effort レベル（例: low / medium / high / xhigh / max）>
- date: <出力日 YYYY-MM-DD>
```

- model: セッションで使用しているモデルID をそのまま記載する
- effort: `/effort` で設定した effort レベルをそのまま記載する（未設定の場合は省略）
- date: 出力時点の日付

### md ファイル出力済みの場合の要約

内容を md ファイルに出力した場合、チャット上では**保存先の絶対パス + 1行サマリ**に留める。ファイルに書いた内容を本文で再掲しない（トークン節約のため）。

例:
```
保存しました: ~/Documents/vault/issues/123-add-new-feature/xxx.md
（調査対象16件中、条件に該当する4件を特定）
```

## 出力テキストの文字種

ターミナル・チャット上での出力（説明文・箇条書き・見出しなど）では、以下の文字種に限定する。

**使ってよい文字種**
- ASCII 英数字・記号（`a-z A-Z 0-9 ! # - * > |` など）
- ひらがな・カタカナ
- 常用漢字
- 句読点（`、。`）・括弧（`（）「」`）

**避ける文字種（代替案）**

| 避ける文字 | 例 | 代替 |
|---|---|---|
| 丸数字 | ①②③ | `1.` `(1)` |
| プライム記号 | ′″ | 省略するか言葉で表現 |
| 囲み文字 | ㈱㊙ | 省略するか言葉で表現 |
| 全角記号 | ～－｜ | 半角 `~` `-` `\|` |
| 絵文字 | ✅❌🔍 | `[x]` `[ ]` など |
| 特殊矢印 | ⇒⟹ | `->` `=>` |

## 使用したコマンドの記載

ドキュメント等に「使用したコマンドを記載して」と依頼された場合は、特に指定がない限り **`等` や `...` で省略せず、実行した／対象となるコマンド・リソースを全て列挙**する。

- 例: `bin/rails routes -g <resource>` を複数リソースに使った場合、「等、リソースごとに」とまとめず、検索した全リソースを1行ずつ列挙する（各行にコメントで対応内容を添えると尚良い）。
- 省略してよいのはユーザーが明示的に許可した場合のみ。
- 理由: 省略すると読者が実際の調査範囲を再現・検証できず、網羅性が伝わらない。

## git の除外設定

ファイルやディレクトリを git の管理対象外にする場合、`.gitignore` でなく `.git/info/exclude` に追加することを優先する。

- `.gitignore` はリポジトリにコミットされ他の開発者に影響するため、個人的なローカル除外には使わない
- ユーザーから明示的に「gitignore に追加して」と指示された場合のみ `.gitignore` を編集する

## 例示のルール

説明・ドキュメント・設定ファイルなどで例を示す際は、特定のタスク・機能・調査内容を示唆しない抽象的な表現にする。

- ブランチ名、ファイル名、サマリ文など、あらゆる例に適用する
- 業務上の特定機能名、バグ内容、調査結果などを例に使わない
- プレースホルダー（`<description>`）や汎用的な語（`add-new-feature`、`fix-bug`）を使う

## URL を根拠とする条件

URL の内容を実際に取得・読み取れた場合のみ、その内容を回答の根拠として使う。

- 取得できていない URL の内容をもとに回答してはならない。読めていないものを読んだかのように扱うのは嘘になる。
- 取得に失敗した場合は、その URL の内容には言及せず、取得できなかった旨を伝える。

## git commit / git push の扱い

- `git commit` と `git push` は、ユーザーが明示的に指示するまで実行しない。
- コミット・プッシュを自発的に提案しない（「コミットしましょうか？」「push しますか？」等を含め、こちらから持ちかけない）。実装や修正が一段落しても、コミット・プッシュはユーザーの指示を待つ。
- ユーザーから明示的な指示があった場合のみ、コミット・プッシュを実行・提案する。

### 例外: 自動コミットの許可

- 環境変数 `CLAUDE_AUTO_COMMIT=1` が設定されている場合は、`git commit` を作業の一環として自発的に実行してよい（提案・確認を省いてよい）。
- この例外は `git commit` のみが対象。`git push` は引き続き指示待ち・確認必須とする。
- フック側も同じ環境変数で連動し、commit のみ確認プロンプトを省く（push 等が混在する場合は確認を維持する）。
